# 增量游戏制作守则 v3

> 来源：《一人做一层 / One Dev One Layer》第一层「虚空成形」的完整迭代。
> 读法：**第零部分**是最高优先级三大总守则；**第一部分**是展开的抽象守则；**第二部分**是具体实例；**第三部分**是工作流；**第四部分**是当前 layer1 状态。

---

## 零、增量游戏开发三大总守则（最高优先级）

1. **不要相信自己的公式运算。**
   当游戏复杂度达到一定程度，任何加成都不能靠列公式预测结果；必须在游戏里实际运行、实际点击、实际重置来测。公式只能用来提出假设，不能用来下结论。

2. **模拟运行必须细颗粒度。**
   粗颗粒度一定会漏掉大量进度与操作（重置、升级、软上限触发点），从而误判真实进度曲线。宁可跑短一点、细一点，也不要用大步长快进代替真实流程。

3. **如非必要，不要让资源产能与资源本体脱钩。**
   例如直接倍增资源库存值。资源应该通过“产能 → 结算 → 库存”的正常路径增长；直接改库存会让玩家看不到成长来源，也会让平衡判断失真。优先做永久产能/倍率/软上限，而不是改存量。

> 下面第一部分的 12 条，都是这三条总守则的具体化。

### 本次违反记录（作为反面教材）

- **公式预测**：75 号软上限、谐振跃迁 `p=1e7`、层2转生收益，都曾按公式推算，结果与实际差了几个数量级（如跃迁直接到 ee10）。
- **粗颗粒模拟**：用 `gameLoop(600)` 大步长快进，且没跑“层2转生 → 第一层重置”，把可恢复状态误判成软锁，也误判了单次重置收益。
- **库存脱钩**：谐振跃迁第一版直接 `points = points.pow(1.5)`，被用户否决；后来改成永久软上限弱化。

## 第一部分：抽象守则

### 1. 节奏是产品
增量游戏的核心不是“数值大”，而是“每隔一段时间有一个可感知的决策或里程碑”。
- 先定目标时间：一个操作到下一个可见进展，尽量控制在 **10 分钟量级**。
- 先模拟再写数值；不要凭感觉写倍率。
- 判据：如果玩家接下来 10 分钟没有新按钮、新升级、新上限或新反馈，这个机制就是装饰。

### 2. 增长曲线不可外推
短窗口的增长率不能代表长期；增量游戏里加速、阶段跳变、反馈回路很常见。
- 不要用前 3 分钟的斜率估算 50 分钟后的状态。
- 一秒涨很多数量级是正常的，不作为“爆炸”判据。
- 看完整曲线，或直接打到里程碑；`idle_lab` 只跑几分钟定下一步，不跑 30/60 天变体。

### 3. 一次只加一个机制，并且先存档
隔离变量，才能知道是哪个改动起了作用。
- 改前复制 `js/layers/layerX.js` 到 `.idle-lab/checkpoints/`；
- 改完立刻测；爆炸可回退；
- 不 `git checkout` 整个文件，避免清掉并发协作者的修改。

### 4. 软上限/硬上限是承重墙
软上限定义了整条曲线的节奏，不是某个升级的私有参数。
- 不模拟就不删除、不绕过、不弱化；
- 新机制优先开新轴，而不是把旧上限打穿；
- 如果需要第二个软上限路径，必须明确它与旧路径是**叠加**还是**互斥**，不能悄悄互相覆盖。

### 5. 存量与流量分开
不要把“库存”当成“收益”来乘。
- 直接写 `player.points = ...` / `voidMine = voidMine.mul(N)` 是改存量；每 tick 一次就是指数爆炸或坍缩；
- 正确做法是给**永久收益公式、永久倍率、软上限**，让库存通过正常结算增长；
- 明确区分：`g`（单次采集收益）、`pointGen`（每秒获取）、`player.voidMine`（库存）。

### 6. `×` 与 `×+` 是两种时间结构
- `×2` 每次翻倍：2、4、8、16——复利；
- `×+2` 每次加 2：3、5、7、9——线性；
- 约定：`×+` 的数值 = 原 `×` 值 − 1；首次数值要与旧效果对齐；
- 写效果时必须说明是乘在 `g` 上还是库存上，是固定乘还是每次采集复利。

### 7. 描述即契约
升级描述是玩家理解数值的唯一入口；描述歧义会被读成完全不同的机制。
- 必须写清：作用对象（数据/虚空矿石/点数/转生点数/冲击）、数学形式（固定乘/复利/加算）、层级（软上限前/后）；
- 避免「每次采集使 X 获取 ×N」这种既可读成单次收益、又可读成库存复利的句子；
- 最好给一个具体数值示例（例如“基础 1e40 → 每次 1e43”）。

### 8. 局部统一，不是全局统一
同一行/同一区域的升级，名称、编号、主题、效果方向要一致；但这只是**局部**约定。
- `xx器MK.y` 是 41–85 这几行的局部格式，不是整个游戏必须遵守的命名法；
- 换一行、换一个主题，可以换一套命名，只要那一组内部自洽。

### 9. 成本是节奏的一部分
价格是玩家“何时能摸到下一个机制”的主要开关。
- 用整齐的 `1eXX`/整数阶梯；同档递增；
- 价格要和当前收入速率匹配，避免买不起或刚解锁就买完；
- 改价格就是改平衡，改完要重新看里程碑时间。

### 10. UI 是机制的一部分
- 显示当前效果、当前倍率、下一档成本、触发条件、是否已激活；
- 不要出现“买了没感觉”“描述和实际不符”的死升级；
- 一次性按钮要明确写“一次性”“已激活”“可与谁叠加”。

### 11. 模拟是风洞，不是公路
`idle_lab` 适合快速比较变体、自动购买、看首次分歧和是否触顶。
- 模型只需覆盖目标循环；不必复刻整个游戏；
- 简化模型的收入/成本/收益可能和真实存档差很远；
- 流程：VM 公式单测 → 几分钟 `idle_lab` → 真实存档/浏览器集成。

### 12. 存档兼容与可回退
- 新状态字段放进 `startData`，旧存档由 `fixSave` 补默认值；
- 改机制前存检查点；改完保留检查点；
- 不要破坏已有存档的加载，也不要在没确认时删除旧机制。

## 第二部分：具体实例

| 守则 | 实例 | 教训 |
|---|---|---|
| 节奏 | 擢升器最初只有 0.1%–1.6% 数据回响，60 天到 e325k | 用户要求“至少快 100 倍”；数值能涨不等于手感对，必须按目标时间调 |
| 外推 | 用 180 秒数据 e4.9M→e6.6M 外推“50 分钟到 e1.2B” | 用户纠正：增长曲线不能外推，且里程碑不应超过 10 分钟量级 |
| 软上限 | 75 号旧的侵蚀软上限弱化 `log10^4e5` | 用户评价“弱化过头”；软上限是承重墙，不能随手削 |
| 存量 | 谐振跃迁曾直接 `points = points.pow(1.5)` | 用户要求“不要直接改库存，给永久加成”；改成永久软上限弱化 |
| 存量 | 共鸣器曾 `g ×= 3125` | 实际是 A（单次收益固定乘），但描述被读成 B/C（库存复利）；数值可接受，问题在描述 |
| `×`/`×+` | 擢升器从“数据 ×”改为“虚空矿石 ×+” | 作用对象换了，旧的 UI/状态/上限都要重新确认 |
| 描述 | “每次采集使虚空矿石获取 ×3125” | 歧义句；正确写法是“每次采集得到的虚空矿石 ×3125（只放大单次收益，库存仍累加）” |
| 命名 | 归航器 → 擢升器 | 用户要的是局部统一；`xx器MK.y` 不是全局命名法 |
| 成本 | MK.I 1e27、MK.IV 2e43、MK.V 1e47；谐振跃迁 2e42/4e42/6e42/8e42 | 价格成阶梯、和收入匹配；MK.V 价格在多轮改动中保持不变 |
| UI | 数据奇点曾写“大幅弱化数据软上限” | 表述不明；后来明确公式/效果，最终整个机制被移除 |
| 测试 | 自动购买测试中临时用 `canAffordUpgrade` 连续买，导致 V 变负 | 买入后要 `updateTemp()`，或用库存直接判断；测试脚本也会制造假 bug |

### 三个深例

**深例 1：A / B / C 的歧义。**
用户问「×3125 是 A、B 还是 C」：
- A：单次收益固定 ×3125，库存线性累加；
- B：每次采集后，下一次收益再 ×1000；
- C：每次采集后把库存 ×3125。

当时的实现是 A，但描述写成“每次采集使虚空矿石获取 ×3125”，被合理读成 B/C。教训：**先写清作用对象，再谈数值**；用户否决时，先确认他理解的是 A 还是 B/C，可能只是描述问题。

**深例 2：谐振跃迁从“改库存”改成“永久软上限”。**
- 第一版：`points = points.pow(1.5)`，用户否决：“不要直接改库存，给永久加成”；
- 第二版：软上限 `p=1e7/2e7/4e7/8e7`，用户实测“一次跃迁暴涨到 ee10”；
- 第三版：`p=1e5/2e5/5e5/1e6`，单次约 e100M 量级，不再 ee10。
- 教训：**不要改库存；软上限指数也要按实际存档调，不能按理论 L 猜。**

**深例 3：数据奇点的加入与移除。**
- 为了跨过 e4e7→e2e8 的墙，曾加“数据奇点”：消耗 e2e8 数据，弱化软上限；
- 后来与 75 号共用 `if/else if` 软上限分支，导致同时拥有时 75 被覆盖；
- 改成软上限之后的 `gain.pow(6)` 独立乘算；
- 最终用户判断“不需要它”，整个机制移除。
- 教训：**同一软上限槽位的多个机制必须明确叠加/互斥；能删的机制要敢删，但删前确认没有其他依赖。**

## 第三部分：工作流

1. **读现状**：目标文件、相关 layer、并发修改；不要假设上一版状态。
2. **定目标**：这一步要让玩家在多少游戏时间内看到什么；不超过 10 分钟量级。
3. **存档**：复制到 `.idle-lab/checkpoints/`。
4. **小步实现**：一次一个机制；优先永久收益/软上限，不改库存。
5. **公式单测**：Node VM + `break_eternity`，测首值、序列、上限、未购买、价格/解锁。
6. **几分钟模拟**：`idle_lab` 或真实存档快进，只看下一步数值和是否触顶；不跑 30/60 天。
7. **真实集成**：UTF-8 静态服务器 + 无头 Chromium + 存档；检查 UI/控制台。
8. **清理与报告**：删除临时文件，保留检查点；报告改动、数值示例、测试结果、文件链接。

### 和用户协作

- 用户给数值/公式时照做，不擅自改结构；有歧义先说明假设。
- 用户说「算了 / 不用了 / revert」时，只回退这次改动，保留已确认内容和并发修改。
- 用户重视手感和“不爆炸”，胜过理论漂亮；先模拟和实测。
- 每轮回复给：改了什么、当前数值示例、测试结果、文件链接、检查点。
